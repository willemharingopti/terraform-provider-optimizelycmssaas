# Importing existing objects

Every resource supports `terraform import`, addressed by the object's **key**. Importing records the object in state; it
does not change it. Write the matching configuration, then run `terraform plan`: the goal is a plan with no changes.

| Resource | Import ID |
|---|---|
| `optimizelycmssaas_locale` | the locale tag, e.g. `sv` |
| `optimizelycmssaas_content_type` | the content type key |
| `optimizelycmssaas_property_group` | the group key |
| `optimizelycmssaas_display_template` | the template key |
| `optimizelycmssaas_application` | the application key |
| `optimizelycmssaas_content_source` | the source key |
| `optimizelycmssaas_content_type_binding` | the binding key |
| `optimizelycmssaas_blueprint` | the blueprint key (generated by the CMS) |
| `optimizelycmssaas_content` | `<key>` for the primary locale, or `<key>/<locale>` |

```shell
terraform import optimizelycmssaas_locale.swedish sv
terraform import optimizelycmssaas_content.welcome 2fa42d46916244e8968cc0127dbd579c/en
```

## A typical workflow

1. **Look first.** The by-key [data sources](../data-sources/content_type) show how an object looks, and the
   [`optimizelycmssaas_manifest`](../data-sources/manifest) data source dumps the whole content model as JSON.
2. **Write the resource** with the values you see.
3. **Import**, then run `terraform plan` and adjust the configuration until it reports no changes.

## When you get `409 Conflict` on create

*"A locale with the key 'sv' already exists"* (and similar) means the object is already on the instance. Import it instead of
creating it. A new instance already has many locales and a handful of built-in objects.

## What cannot be managed

Built-in objects the CMS defines itself, for example system content types such as `ImageMedia`, the built-in property
groups, and the built-in content sources, cannot be changed or deleted through the API. Read them with data sources.
Property formats are read-only and available only as a data source.

## After an import

- For `optimizelycmssaas_content_type`, the imported `properties_json` is the API's complete representation, including
  defaults. Your configuration will usually contain only the fields you set, so the **first plan after an import shows an
  in-place update** of `properties_json`. Applying it changes nothing in the CMS (it only re-sends your fields) and records
  your version; later plans are clean.
- For `optimizelycmssaas_application`, the CMS stores `entry_point` without a `?loc=` part. If you write one in your
  configuration, expect the same one-time in-place update after the import.
- Create-only attributes (such as `blueprint` on content) are not returned by the API and stay empty after an import.
