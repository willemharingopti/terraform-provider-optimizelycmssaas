# Modelling content

## Content types

A content type defines the shape of a content item. Its `base_type` decides what it is and where it can be used:
`_page`, `_component`, `_media`, `_image`, `_video`, `_folder`, `_experience`, `_section` or `_element`. The `key` and
`base_type` cannot be changed after creation; changing either replaces the type.

```terraform
resource "optimizelycmssaas_content_type" "article" {
  key          = "Article"
  base_type    = "_page"
  display_name = "Article"

  properties_json = jsonencode({
    heading = { type = "string", displayName = "Heading", isRequired = true, maxLength = 120 }
    body    = { type = "richText", displayName = "Body", group = optimizelycmssaas_property_group.seo.key }
    tags    = { type = "array", displayName = "Tags", items = { type = "string" } }
  })
}
```

### Properties

`properties_json` is a JSON object keyed by property name. Each property has a `type`:
`string`, `url`, `boolean`, `integer`, `float`, `dateTime`, `contentReference`, `content`, `link`, `richText`, `json`,
`array`, `component` or `composition`. Other common fields are `displayName`, `description`, `group`, `sortOrder`,
`isLocalized`, `isRequired`, `minimum`/`maximum`, `minLength`/`maxLength`, `pattern`, `enum`, `allowedTypes` and
`restrictedTypes`. The list of property *formats* available is exposed by the
[`optimizelycmssaas_property_format`](../data-sources/property_format) data source.

The provider passes the JSON through unchanged, so any property field the API supports works without a provider update.

**Drift detection.** The CMS adds defaults to every property (for example `isLocalized = false` and
`sortOrder = 0`). The provider compares what you wrote with what the API returns *structurally* and ignores fields you
did not set, so these defaults do not produce a diff. A property that is added, removed or changed outside Terraform does.

### Changing and removing properties

- **Adding or changing** a property is an in-place update.
- **Removing** a property deletes the values stored for it in existing content. The CMS therefore refuses it with
  *"The changes ... are considered breaking and could potentially result in data loss."* To allow it, opt in explicitly:

  ```terraform
  resource "optimizelycmssaas_content_type" "article" {
    # ...
    allow_data_loss = true
  }
  ```

  Leave it `false` (the default) and the apply fails with the CMS's message instead of silently losing data.

### Who may create content of a type

`access_rights` restricts *who can create* content (and blueprints) of a type. Without it, everyone can. If you set it,
make sure the API client you run Terraform with belongs to one of the listed roles, or creating content of that type
fails with `403`.

```terraform
access_rights = [{ name = "WebAdmins" }] # type defaults to "role"; also "user" or "application"
```

## Property groups

[`optimizelycmssaas_property_group`](../resources/property_group) organises properties in the editor. Reference the group
by key in a property's `group` field. The CMS ships a few built-in groups (such as `Content` and `Settings`); they are
read-only.

## Display templates

[`optimizelycmssaas_display_template`](../resources/display_template) defines settings that editors can choose for
content, for example a width. Attach it to a `content_type`, a `base_type` or a `node_type`. Settings and their choices
are typed attributes, so a plan shows exactly which setting or choice changes.

The CMS makes the first display template for a type the default regardless of `is_default`, so leave `is_default` unset
unless you need to control it.

## Blueprints

[`optimizelycmssaas_blueprint`](../resources/blueprint) is a template of property values that is used when creating new
content. The `key` is generated by the CMS when you omit it.

~> **Property values are wrapped.** In `content_json` (and in `properties_json` on content items) each value is an
object with a `value` field: `{ title = { value = "Hello" } }`. A bare string is rejected by the API.

## Content sources and content type bindings

[`optimizelycmssaas_content_source`](../resources/content_source) and
[`optimizelycmssaas_content_type_binding`](../resources/content_type_binding) connect the CMS to external content
(for example Optimizely Graph). A binding maps one content type, and its properties, onto another. The CMS ships built-in
sources (`Item`, `AssetItem`, and so on); you can read them with the data sources and manage your own with the resources.

## Locales

[`optimizelycmssaas_locale`](../resources/locale) adds a language. The key is an IETF BCP-47 tag (`en`, `en-GB`, `sv`),
and `fallback` names the locale to use when content is missing. A new instance already has many locales, so adding one
that exists returns `409`; import it instead (see [Importing existing objects](importing-existing-objects)).

## Comparing environments

The [`optimizelycmssaas_manifest`](../data-sources/manifest) data source exports the content model (locales, property
groups, content types and display templates) as JSON, which is useful for diffing two environments. *Importing* a
manifest is intentionally not supported: it is a bulk operation that can lose data and has no sensible way to be undone.
